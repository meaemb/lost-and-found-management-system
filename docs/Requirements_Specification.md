# 6. Requirements Specification

## 6.1. Introduction

This section defines the functional and non-functional requirements of the proposed Multi-Organization Lost and Found Management System.

The requirements are based on the Project Proposal, preliminary user research, literature review, analysis of existing lost and found systems, and the intended scope of the project. The specification describes the expected behavior of the system, the responsibilities of different user roles, and the quality requirements that should be considered during design, implementation, and evaluation.

The system is intended to support four main user roles: General User, Organization Employee, Organization Administrator, and Platform Administrator. Access to system functionality will depend on the authenticated user's role and organizational affiliation.

## 6.2. User Roles

The system will support four primary user roles.

| Role | Description | Main Responsibilities |
|---|---|---|
| General User | An individual using the platform to report or search for lost and found belongings | Submit lost and found reports, search items, review potential matches, submit ownership claims, and track statuses |
| Organization Employee | An authorized employee responsible for lost and found operations within an organization | Register found items, manage assigned records, review ownership claims, and update return statuses |
| Organization Administrator | A representative responsible for managing lost and found operations within a specific organization | Manage organization employees, monitor organizational records, and oversee claims and return processes |
| Platform Administrator | A system-level administrator responsible for the overall platform | Manage participating organizations, platform-level access, and administrative operations |

The role model is intended to separate ordinary user functionality from organizational and platform administration. Organization employees and administrators should only receive access to information and operations permitted by their roles and organizational affiliation.

## 6.3. Functional Requirements

Functional requirements describe the operations that the system must provide.

### 6.3.1. User Authentication and Account Management

| ID | Functional Requirement |
|---|---|
| FR-01 | The system shall allow users to create an account. |
| FR-02 | The system shall allow registered users to authenticate using their credentials. |
| FR-03 | The system shall allow authenticated users to log out. |
| FR-04 | The system shall associate authenticated accounts with an appropriate system role. |
| FR-05 | The system shall restrict protected functionality according to the authenticated user's role. |

### 6.3.2. Lost and Found Item Reporting

| ID | Functional Requirement |
|---|---|
| FR-06 | The system shall allow authenticated users to submit lost item reports. |
| FR-07 | A lost item report shall contain relevant information such as item category, description, color, date, and approximate location. |
| FR-08 | The system shall allow users to provide additional item characteristics, such as brand, model, distinguishing features, or photographs when applicable. |
| FR-09 | The system shall allow authorized organization employees to register found items associated with their organization. |
| FR-10 | The system shall allow users to view and manage their own submitted reports. |
| FR-11 | The system shall allow authorized organization employees to update records for found items managed by their organization. |
| FR-12 | The system shall maintain a status for lost and found item reports. |

### 6.3.3. Search and Filtering

| ID | Functional Requirement |
|---|---|
| FR-13 | The system shall allow users to search available lost and found item records. |
| FR-14 | The system shall provide filtering based on selected item attributes such as category, location, and date. |
| FR-15 | The system shall allow appropriate records from participating organizations to be searched through a unified interface. |
| FR-16 | The system shall prevent sensitive or restricted information from being displayed in public search results. |

### 6.3.4. Automated Item Matching

| ID | Functional Requirement |
|---|---|
| FR-17 | The system shall compare lost and found item reports to identify potential matches. |
| FR-18 | The matching mechanism shall consider selected structured attributes, including category, color, date, location, brand, model, or other available characteristics. |
| FR-19 | The system shall calculate or determine the similarity between relevant lost and found reports using defined matching rules or scoring criteria. |
| FR-20 | The system shall present potential matches to relevant users or authorized employees. |
| FR-21 | A potential match generated by the system shall not automatically establish ownership of the found item. |

The initial matching implementation will use a rule-based or similarity-scoring approach. Advanced machine learning or image recognition is not required for the initial project scope.

## 6.4. Ownership Claim and Verification Requirements

Ownership verification is treated as a separate process from automated matching.

| ID | Functional Requirement |
|---|---|
| FR-22 | The system shall allow an authenticated user to submit an ownership claim for a potentially matching found item. |
| FR-23 | The system shall allow the claimant to provide supporting ownership information. |
| FR-24 | The system shall support verification information that is not publicly visible to other users. |
| FR-25 | The system shall allow authorized organization employees to review ownership claims associated with items managed by their organization. |
| FR-26 | The system shall allow an authorized employee to approve or reject an ownership claim. |
| FR-27 | The system shall record the current status of each ownership claim. |
| FR-28 | The system shall prevent an automatically generated potential match from being treated as an approved ownership claim without verification. |

Supporting information may include distinguishing characteristics, information not visible in public photographs, previous photographs of the item, receipts, device-specific information, or other evidence appropriate to the item type.

The exact verification procedure may vary depending on the sensitivity or value of the item and remains subject to review by an authorized organization employee.

## 6.5. Return Process Tracking

After an ownership claim has been approved, the system should support tracking of the return process.

| ID | Functional Requirement |
|---|---|
| FR-29 | The system shall allow authorized employees to update the return status of an approved item. |
| FR-30 | The system shall allow the relevant user to view the current status of the return process. |
| FR-31 | The system shall maintain a history of relevant status changes. |
| FR-32 | The system shall allow an item to be marked as returned after the recovery process has been completed. |

The system will track the administrative status of the return process but will not physically collect, store, transport, or deliver belongings on behalf of participating organizations.

## 6.6. Notification Requirements

| ID | Functional Requirement |
|---|---|
| FR-33 | The system shall notify relevant users when significant changes occur to their reports or claims. |
| FR-34 | The system shall notify a user when a potential match is identified where applicable. |
| FR-35 | The system shall notify a claimant when an ownership claim is approved or rejected. |
| FR-36 | The system shall notify relevant users about significant changes in the return process status. |

The implementation of notification channels will depend on the final system design. The initial version may provide in-system notifications, while additional channels may be considered later.

## 6.7. Organization Management Requirements

The system is designed to support multiple participating organizations within one platform.

| ID | Functional Requirement |
|---|---|
| FR-37 | The system shall maintain separate participating organization records. |
| FR-38 | Found items registered by organization employees shall be associated with the appropriate organization. |
| FR-39 | Organization employees shall only be allowed to perform restricted administrative operations for organizations to which they are authorized. |
| FR-40 | Organization administrators shall be able to manage authorized employees within their organization. |
| FR-41 | Organization administrators shall be able to monitor lost and found activities associated with their organization. |
| FR-42 | The platform administrator shall be able to manage participating organizations. |
| FR-43 | The system shall prevent unauthorized cross-organization administrative access. |

These requirements are particularly important because the proposed platform combines shared search functionality with organization-specific administrative responsibilities.

## 6.9. Main System Workflows

The requirements can be organized into several main workflows.

**Lost Item Workflow:** A user authenticates, creates a lost item report, provides item characteristics and approximate loss information, and submits the report. The system stores the report and evaluates relevant found item records for potential matches.

**Found Item Workflow:** A user or authorized organization employee registers a found item. When the item is managed by a participating organization, the record is associated with that organization. The system evaluates relevant lost item reports for potential matches.

**Matching Workflow:** The system compares compatible lost and found reports using selected attributes and defined matching criteria. Potential matches are presented to relevant users or employees for further review.

**Ownership Claim Workflow:** A user selects a potentially matching found item and submits an ownership claim with supporting information. An authorized employee reviews the claim and approves or rejects it. Automated matching alone does not determine ownership.

**Return Workflow:** After an ownership claim is approved, an authorized employee updates the return process status. The claimant can monitor relevant status changes until the item is marked as returned.

**Organization Management Workflow:** Organization administrators manage authorized employees and monitor records associated with their organization, while the platform administrator manages participating organizations and platform-level administration.

## 6.11. Conclusion

This section defined the functional and non-functional requirements of the proposed Multi-Organization Lost and Found Management System.

The functional requirements cover authentication, lost and found item reporting, search and filtering, automated matching, ownership verification, return tracking, notifications, and multi-organization management.

The non-functional requirements address security, privacy, usability, performance, maintainability, compatibility, and accessibility.

A key requirement of the proposed system is the separation between automated match identification and ownership verification. A potential match only indicates that two reports may refer to the same item; the item should not be returned until an authorized verification process has been completed.

The requirements defined in this section will provide the basis for the system architecture, interface design, implementation, and subsequent verification and evaluation activities.
